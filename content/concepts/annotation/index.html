ANNOTATION — definition of record
An annotation is a thread attached to a rendered page, either to a quoted passage or to the page as a whole. It is stored in a committed sidecar file beside the page, anchored by the quoted text and a little of its surrounding context rather than by the page's markup. It is one of two kinds: a question, which a reader opens and which waits until whoever acts on the page addresses or declines it, or a flag, which an agent leaves on a passage it wrote beyond its source and which rests as noted, asking nothing until the reader keeps it or asks for a change. It moves through five states: open, noted, addressed, declined and withdrawn. Nothing needs to be running for it to survive; the file is the only channel between the two sides.

Why it matters

Review usually needs both parties present: a live comment tool, a pull request someone is watching, a chat. Pages written by agents are read later, by people whose time does not line up with any agent session. Putting the note in a file beside the page, in the repository, makes the note outlive both the reading and the session that will answer it, and makes the whole exchange part of the history.

Anchoring by quote instead of by position is what lets a page keep changing while notes are pending. A CSS path breaks the moment a paragraph is added above; a quoted sentence is still findable as long as the sentence exists. The shape is the W3C Web Annotation TextQuoteSelector: the exact text, plus up to 32 characters before and after it to tell repeated passages apart.

Worked example

A reader of a bird-watching note selects "arrive with the first warm front" and asks which front. The engine writes content/notes/swifts-follow-weather.annotations.json:

{
  "version": 1,
  "page": "/content/notes/swifts-follow-weather.html",
  "threads": [
    {
      "id": "t-20260922-7b8ecb",
      "created": "2026-09-22T20:43:59Z",
      "author": "sam",
      "state": "open",
      "target": {
        "type": "TextQuoteSelector",
        "exact": "arrive with the first warm front",
        "prefix": "",
        "suffix": ""
      },
      "body": "Which front? Say how you would see it on a forecast.",
      "replies": []
    }
  ]
}

Days later an agent runs ckit annotations list, rewrites the sentence to name the front, and replies in the thread with --state addressed. The reply says what changed. The thread stays in the file, with its reply, for good.

The loop runs the other way too. Writing the note's companion entry, an agent adds a paragraph the source never said and leaves a flag on it, --kind flag --label "worked example". The flag rests as noted: the passage is marked on the page and listed on the review page, and nobody is waiting. The reader, weeks later, presses Keep under it, or Ask for a change, and the thread opens with that instruction for the next agent.

Common trap

Editing the page before answering the notes on it. An open thread's quote is load-bearing. Rewrite that sentence first and the gate goes red: 
content/notes/swifts-follow-weather.annotations.json: thread t-20260922-7b8ecb has a STALE anchor — 'arrive with the first warm front' is no longer on the page
A dropped comment is not a resolved one. Address the thread (or decline it, with the reason) in the same change that rewrites its passage. Once a thread is no longer open its anchor is history and is not checked: acting on a note usually changes the text it quoted. A noted flag whose passage is rewritten is named as stale by the lint and never fails it: withdraw the flag, and flag the new passage if it still goes beyond the source.
