Extension point

Definition of record. A declared place where a repository adds to the engine without changing it, and why each one is checked.

EXTENSION POINT — definition of record
An extension point is one of the ten keys in kit.json through which a repository, or a layer installed into it, adds to what the engine does without changing the engine: genres, checks, generators, chronicle.extractors, shell_pages, links, refs, theme, classes and indices. The gate validates every declaration, and one that is malformed, points at nothing, or names a check no module provides fails it by name.

Why it matters

Every library eventually needs something the core does not have: a genre for its own kind of page, a rule only its pages must follow, a page of its own in the shell. Without a declared place to put that, the choices are to fork the kit or to keep the rule in someone's head. An extension point is the third choice: the addition lives in the repository, in one file a reader would look at, and the engine loads it on every run.

Validation is the other half. A declaration the engine quietly ignored would be worse than none, because the author would believe it was running. So a theme that does not exist, a shell page that would shadow one of the shell's own files, a reference pattern with a capturing group, or a genre naming a check nobody implements each stops the gate with a message naming the key.

Worked example

A bird-watching library wants a page per sighting, each naming where it happened. It declares a genre and the check that holds it:

"genres": {
  "sighting": { "dir": "sightings", "layout": "flat", "skeleton": "note.html",
                "register": "dated, one bird, one place", "reader": "another watcher checking a record",
                "forbidden": "undated sightings", "after": "hub", "label": "Sightings",
                "checks": { "status": true, "require_place": true } }
},
"checks": ["ext/checks_birding.py"]
# ext/checks_birding.py
import re

PLACE = re.compile(r'<meta name="place" content="[^"]+"')

def require_place(ctx):
    return [] if PLACE.search(ctx.served) else [f"{ctx.rel}: a sighting needs <meta name=\"place\" content=\"…\">"]

CHECKS = {"require_place": require_place}

Before the module was registered, the lint refused to run at all:

genre 'sighting' names check 'require_place', which is not a core check and no module in kit.json `checks` provides — register the module that implements it, or drop the check from the genre

With it registered, ckit new sighting 2026-05-03-swifts scaffolds a page, the Sightings group appears in the sidebar right after the hubs, and the new page fails by name until it says where the swifts were.

Common trap

Editing the vendored kit instead of declaring. Changing a file under kit/ is quicker than adding a key, and it makes this repository's rules silently different from every other's. The pin catches it: 
kit: VENDORED COPY HAS DRIFTED FROM ITS PIN
The change belongs upstream if it is a mechanism every library needs, and in kit.json if it is this library's own.

Related concepts

Extension points add genres (with their skeletons), checks for the gate, and extractors for the chronicle. Which additions belong in a repository or a layer, and which belong in the engine, is the placement rule.
