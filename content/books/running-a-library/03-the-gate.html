The gate

You leave knowing what ckit check runs, in what order, what each failure looks like, and why it never fixes anything for you.

§1 · Six stages, in order

The gate is ckit check. make check runs it after one more step, make kit-verify, which you met with the pin. Here is what it does, in the order it does it:

StageHolds whenFails like
1 · pinkit.json declares the engine version that is runningengine mismatch: kit.json declares ckit 0.3.2, this engine is 0.4.0.
2 · shellthe shell's lib.css is where kit.json says the shell isno vendored shell at kit/shell — run `ckit init` here
3 · declarationsevery extension kit.json declares holds, and home, if set, names a page that existskit.json theme: 'assets/theme.css' does not exist
4 · indicesevery generated file equals what the content would generate nowindices out of date — run `ckit nav` (or `ckit lint`) and commit the result
5 · lintevery page passes its form and its genre's checks, and every annotation sidecar validatesnote has <h2> sections — a note is one claim; promote it
6 · booksevery book passes the node verifierbook verify failed: content/books/…

Stages 1 to 3 are preconditions: the first of them that fails stops the run, because nothing after it can be trusted. From stage 4 on, every stage runs and reports, and the gate exits 1 at the end naming each stage that failed, so one run shows every problem. Nothing is rewritten, nothing needs the network, and the same command gives the same answer in CI. When every stage holds you see:

$ ckit check
content lint clean — 2 file(s)
content check ok

The book verifier, stage 6, reads each book's pages with node: it checks that structural tags are balanced, runs every inline script against a stub of the page, and follows every relative link and #anchor between the book's pages. The gate refuses to skip it: if the library has a content/books/ directory and node is not installed, the gate fails and says so.

Check-yourself: the gate reports stale indices and three lint problems. You run ckit lint, which regenerates the indices, and the gate still fails. Why?
ckit lint regenerates the indices and fixes nothing else: the three lint problems are still there, and the gate reports all of them in the same run. Fix them, run ckit lint again (your edits changed the indices), then the gate.

§2 · Stale indices

Some files under content/ are generated from the pages: catalog.json (the sidebar and landing page), search-index.json, backlinks.json (who links to whom), a nav.json for each book, chronicle.json when the library declares a record, and whatever a generator the library registers writes. They are committed, because the served site reads them as they are.

Two commands treat them differently, on purpose. ckit lint regenerates them. ckit check only compares:

$ ckit check
indices out of date — run `ckit nav` (or `ckit lint`) and commit the result:
  content/catalog.json
  content/search-index.json
  content/backlinks.json

If the gate rewrote them instead, a commit that forgot to regenerate would pass, and the committed files would still be wrong for everyone who checked the repository out. Failing puts the fix in the commit that caused the problem. The habit is short: after writing, run ckit lint, then commit the pages together with every file it reports it refreshed.

Check-yourself: you change the <title> of a chapter. Which generated files go stale?
At least the book's nav.json (it lists chapter titles) and search-index.json; backlinks.json too if the chapter links to other pages, since it records the citing page's title. You do not need to work it out: run ckit lint and commit what it wrote.

§3 · What the lint reads

The lint reads each page's source and applies two sets of rules. The form rules are the same for every page:

  • No raw hex colour anywhere in the page. Colours come from the shell's tokens.
  • No var(--name) that neither the shell, the library's theme, nor the page itself declares. An undeclared token renders as nothing, silently.
  • Every class that looks like shell vocabulary (starting sw-, lane-, v-, ev-, st-, hb-) is one the shell or the library defines.
  • The page loads /shell/lib.css.
  • Every internal href and src resolves the way the exported site would serve it: no address nothing answers, no directory without an index.html, no bare slug, no letter-case mismatch, no file git ignores, and no address the library has moved. A skeleton's placeholder links are reported until they point somewhere real; data-unchecked exempts a link the gate cannot see, such as a build product.
  • One paragraph per line: no prose element broken across lines at a column. ckit unwrap joins them.
  • Tags are lowercase slugs, each once per page.
  • The page lives under a genre. A page anywhere else under content/ is an error.
content/notes/swifts-follow-weather.html: unknown shell class 'sw-sky'
content/notes/swifts-follow-weather.html:14: unknown token var(--sky) — not a shell token; name it in the repo's theme (kit.json "theme") or declare it on the page

The genre rules are the ones a page's genre switches on:

CheckCatchesCore genres using it
statusa status the first <p class="sub"> states that the shell does not knowall
max_wordsa page over its boundnote 400 · concept 1500 · hub 1500
no_h2sections in a page that is one claimnote
require_defnno blockquote.defn with a .defn-nameconcept
no_forward_refsa link to a later chapter without data-fwdchapter
require_meta_statusno active, shipped or paused lifecycle metaproject
require_sectionsdeclared <h2> ids missing or out of ordernone; for genres a library adds

One consequence of reading source text: a code sample on a page is read too. A hex colour, an unknown class="…" or an undeclared var(--…) inside a <pre> fails exactly like one in the page itself. When a page has to show one, escape the character the lint keys on: &#35; for the #, &quot; for the quotes, &#40; for the parenthesis. The reader sees the same text. Structural checks, on the other hand, read only what a reader is served: a section that exists only inside an HTML comment does not count.

Check-yourself: your page uses style="color: var(--sky)" and fails. Name two fixes.
Use one of the shell's hues instead (var(--azure), say), or declare --sky in the library's theme, or on the page itself if only that page uses it.

§4 · The fixture rule

How do you know a check works? Not by reading it. The engine answers with its own gate, ckit selftest: it builds a scratch library, scaffolds one page of every core genre (each must lint clean), then plants one page designed to break each check, and fails unless every planted problem is reported by name. The engine repository's make check runs that, plus an end-to-end run that installs the kit into a scratch repository and drives every command.

The rule behind it is short: a check ships with a fixture designed to break it, or it is not a check. The engine holds itself to it. When your library adds a check of its own (the last chapter shows how), hold yours to it too: plant a page that should fail, watch it fail by name, then delete the plant. Nothing in the engine can force that on your check. That part is discipline. The design law says why it matters.

Check-yourself: you write a check that no note may contain "TODO". What are its fixtures?
A note with TODO in its prose, which must be reported by name; and a note with TODO only inside an HTML comment, which must pass, because a check should read what a reader is served. Without the first you do not know it fires; without the second you do not know it fires only when it should.

§5 · Annotations, anchored

Readers can leave notes on a rendered page, stored in a sidecar file beside it; the next chapter covers the whole loop. The gate's part is this. Every sidecar must be well-formed: version 1, the page it names is the page beside it, thread ids unique, states valid, a declined thread carrying its reason. And every open thread's quoted passage must still be on its page:

content/notes/swifts-follow-weather.annotations.json: thread t-20260922-7b8ecb has a STALE anchor — 'arrive with the first warm front' is no longer on the page

That message means the page was edited around an unanswered note. Answer the thread in the same change, and the gate is green again. Threads that are no longer open are not checked this way: acting on a note usually changes the words it quoted.

Check-yourself: an addressed thread quotes a sentence you have just deleted. Does the gate fail?
No. Only open threads' quotes are held to the page. The addressed thread's reply records what was done, and its quote is history.
