The review loop

You leave knowing how to annotate a page, have an agent answer it later, and review what an agent added beyond its source, all from the browser.

§1 · Annotating in the browser

Serve the library with make docs and open any page. A passage that already has an annotation is underlined with dots: amber for a question waiting for an answer, blue for a passage an agent flagged. Click one and the annotation panel opens on it.

The ✎ Annotate button, bottom right, opens the panel too. On a wide screen the panel sits beside the text; on a narrow one it is a sheet along the bottom. There are two ways to annotate:

  • On a passage. Select some text. A ＋ Comment on selection button appears; write your comment and save it.
  • On the whole page. Press ＋ Comment on the page in the panel, for something about the page's shape, its genre or its status.

The first time, the browser asks for your name and remembers it: every annotation needs an author. The panel lists each thread (an annotation and its replies) with its state and the passage it quotes. A thread whose passage is no longer on the page is marked as a stale anchor.

Under a waiting thread the panel offers Reply, Keep (close it as accepted) and Decline (with the reason the gate requires). Under a closed one it offers Reopen, and under one you wrote, Withdraw. A link ending in #ann=<id> opens the panel on that thread; the home page and the review page link this way.

The button appears only when the engine serves the page. When a page loads, the shell asks the server whether it takes annotations (/__annotations/ping). The engine says yes; a static host answers "not found". So a published copy of the library never shows the button, and no reader of it can annotate by accident.

Nothing checks who writes an annotation: anyone who can reach the server can write one into your repository. So the engine serves on this machine only. ckit serve --host with an address that is not this machine is refused unless you add --expose. Even on this machine, the server answers only requests addressed to 127.0.0.1 or localhost, and takes an annotation only from a page it served.

Check-yourself: why can't a reader of the published site annotate it?
No engine stands behind it to save the annotation. The shell's question gets "not found", so it never loads the annotation panel, and the button never appears.

§2 · What an agent flags

Not every thread starts with a reader. An agent that writes a page from a source sometimes adds something the source did not say: a worked example, a framing, a claim from memory. The /present skill has it leave a flag on that passage. A flag is the second kind of thread. Its label says what was added, and it rests in the state noted.

A flag asks nothing. It marks the passage on the page and counts on the review page, so you can see at a glance what came from the source and what the agent added. No one waits on it.

Under a flag the panel offers Keep, which closes it as accepted, and Ask for a change, which takes your instruction and opens the thread. From then on it is a waiting thread like any other, and the next agent to run /address acts on your reply.

A question is different. An agent opens one only where your answer changes the page: a claim it could not verify, or a choice bigger than one page. It opens waiting. The home page counts the questions under Waiting for you and names the flags on a separate line, because the two ask different things of you.

Check-yourself: an agent left twelve flags and one question on a chapter. What is waiting for you?
The one question. The twelve flags rest as noted. Read them when you read the chapter, then keep them or ask for a change, one at a time or all at once from the review page.

§3 · The sidecar

A saved annotation goes into a file beside the page, called its sidecar, and is committed with the page. A flat page's sidecar is named after the page; a folder page's is named after its index.html:

PageIts sidecar
content/notes/swifts-follow-weather.htmlcontent/notes/swifts-follow-weather.annotations.json
content/concepts/flyway/index.htmlcontent/concepts/flyway/index.annotations.json

Inside is a list of threads. Each has an id, an author, a date, a kind and a label, a state, a body and its replies. It also has a target: the quoted passage, or null for an annotation on the whole page. The target follows the W3C Web Annotation TextQuoteSelector: the exact text, and up to 32 characters on either side to tell a repeated phrase apart. The quote is stored as text, not as a position in the markup, so the page can change around it.

That file is the whole channel. No server has to stay up, and no agent has to be listening. The annotation waits in the repository until someone acts on it; after that, the thread and its reply stay in the file for good.

Check-yourself: where is the sidecar for /content/concepts/flyway/, and what goes in its target for an annotation about the whole page?
content/concepts/flyway/index.annotations.json; the target is null.

§4 · ckit annotations

The same threads, from the command line, in any session and on any clone:

$ ckit annotations list
open      /content/notes/swifts-follow-weather.html  t-20260922-7b8ecb  [sam]

          Which front? Say how you would see it on a forecast.
VerbDoes

Name a page the way the browser does (/content/notes/swifts-follow-weather.html, /content/concepts/flyway/) or by its path in the repository.

Check-yourself: how do you see every thread anyone has already closed as addressed?
ckit annotations list --state addressed, or --state all for everything.

§5 · /address

An agent works through open threads with the /address skill, which ckit init linked into the repository. The loop:

  1. List what is open: ckit annotations list.
  2. Read the page, not just the quote. Find the passage in context and read the genre's voice. The fix must keep that voice: an annotation on a concept's definition is not answered by adding a paragraph under it.
  3. Decide, then do one of two things. Address it: edit the page, then reply with what changed, precisely enough to check without a diff, and --state addressed. Or decline it: reply with the reason and --state declined. Nothing in between, and never addressed for a partial fix.
  4. Run the checks: ckit lint, then make check.
  5. Commit the page and its sidecar together, one commit per page, so a reviewer reads one page's change at a time.
$ ckit annotations reply /content/notes/swifts-follow-weather.html t-20260922-7b8ecb \
    --author "agent:claude" --state addressed \
    --body "Named the front: the first day the overnight low stays above 10 °C."
t-20260922-7b8ecb → addressed

A few rules keep the file trustworthy. Never delete a thread, and never edit a sidecar by hand: a state moves only through the browser or ckit annotations. Reply as yourself, agent:<name>, so the record shows who acted. Only a thread's author withdraws it.

Flags are not the agent's to close. A noted flag rests until you keep it or ask for a change, and a thread you reopened that way carries your reply as the instruction. When a thread asks for a number, the answer gives the number with its source, or says that nothing supports one yet and leaves the thread open.

Check-yourself: a reader asks for a concept's definition to include this year's swift count. What do you do?
Decline, with the reason: a concept's definition must stay true when the count changes. The reply can offer what the genre allows: the count below the definition, with its source.

§6 · What the gate holds you to

The previous chapter showed this failure from the gate's side. From the author's side it is one habit: address before you edit. If the page you are about to rewrite has open threads, answer them in the same change. Rewrite a passage that an open thread quotes, leave the thread open, and the gate fails with a stale anchor until the thread is answered.

The gate also refuses a declined thread with no reason in its replies, a sidecar whose page has gone, and a sidecar that names the wrong page. A closed thread keeps its quote as history, unchecked. A noted flag whose passage was rewritten is named by the lint as stale, and never fails it: there is nothing left to disclose, so the agent withdraws it, and flags the new passage if that too goes beyond the source.

Check-yourself: you are rewriting a page with two open threads, one on a paragraph you are rewriting and one on a paragraph you are keeping. What has to happen in this commit?
The thread on the rewritten paragraph must be addressed (or declined, with its reason) in the same change. The other can stay open: its quote is still on the page.

§7 · Review, the page

One page shows every thread in the library: /shell/review.html. While the engine serves a library that has any thread, Review appears in the library rail, with a badge counting the questions waiting.

It reads content/threads.json, an index the engine generates with the others and updates after every annotation, so one you just left never puts the checks out of date. It groups the threads by page or by label, and filters them: waiting, noted, settled. Each thread links to its passage on the page.

A whole group can be kept at once: twelve worked examples, one press. Questions stay one at a time, where they belong. The exported site carries neither the index nor the page: review is work on the library, not part of what it publishes.

Check-yourself: why does the review page disappear from an exported site?
The sidecars it is built from are not exported, and neither is the index made from them. A static host has no engine to act on a thread, so the page would have nothing to read and nothing to do.
