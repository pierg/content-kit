Install a library

Status: LIVE — you leave with the engine on your machine, a repository with the kit in it, a gate that passes, and its pages open in your browser.

§1 · The engine

content-kit comes in two halves. One is an engine, a command called ckit, which you install once per machine. The other is a kit of rules (a shell of styles and scripts, the genres, the layout playbooks, two agent skills) which the engine copies into each repository you use it in. Start with the engine.

uv tool install git+https://github.com/pierg/content-kit@v0.4.0
$ ckit version
0.4.0

The engine is plain Python, 3.10 or newer, with no dependencies. It also needs node, for one job: the gate verifies books with it, and asks for it in any library that has a content/books/ directory, which every library ckit init scaffolds does. If you do not use uv, clone the repository and run bash install-engine.sh in it: that links the checkout's bin/ckit into ~/.local/bin, and from then on git pull in the checkout is how you upgrade.

Why install the engine at all, instead of copying it into every repository like the rules? Because it is code, and code you copy ten times you fix ten times. The rules are different: an agent opened in a repository must be able to read them there, with nothing to resolve elsewhere, so they are copied in. The next section shows how the two stay honest with each other.

Check-yourself: which half lives in the repository, and why?
The kit (shell, genres, playbooks, skills) is copied into the repository, because an agent working there must read the rules without looking anywhere else. The engine is installed once per machine, because it is code with one place to update.

§2 · ckit init

Point ckit init at a directory (new or existing) and give the library a name:

$ ckit init birding --name "Birding"
vendoring content-kit 0.4.0 -> …/birding/kit
scaffolding
  create  kit.json
  create  Makefile
  create  .gitignore
  set     kit.json name=Birding
  pin     kit.json ckit=0.4.0
pinned  content-kit@v0.4.0
indices generated: content/catalog.json, content/search-index.json, content/backlinks.json

Read it line by line. It vendored the kit into kit/: the shell, the genres, the craft playbooks, the /present and /address skills, a hashing tool and verify.sh. It scaffolded what the directory lacked: kit.json, a Makefile, a .gitignore, and the directories under content/ that the core genres live in. It pinned the engine version into kit.json and wrote kit/PIN. It linked the two skills into .claude/skills/, so an agent session opened in the repository finds them. And it generated the three indices an empty library has.

Running it again is safe. It re-vendors kit/, re-pins, and creates only what is missing: your Makefile, your kit.json settings and your pages are kept. It touches only its own paths under kit/, so anything else vendored there survives.

PIN — definition of record
A library's pin is two records of what it was checked against: the engine version in kit.json (the "ckit" key), which ckit check compares with the engine running it, and a hash of the vendored kit/ in kit/PIN, which make kit-verify recomputes. Either mismatch fails; neither changes except on purpose. 
$ cat kit/PIN
source content-kit https://github.com/pierg/content-kit v0.4.0
hash 722ee4c53ef1b42a8104b2d87f747ce4e06eaa8ffb1c2d3ec51a9b169ddb3684

The source line says where the kit came from and at which release (a commit, when the engine runs from a checkout). The pin is why installing a new engine never silently changes a library: until someone re-runs ckit init in it, the gate refuses to run under a different version.

Check-yourself: you upgrade the engine to a new release and run the gate in an old library. What happens, and what is the deliberate fix?
The gate fails with an engine mismatch: kit.json still declares the old version. Re-running ckit init . with the new engine re-vendors the kit and moves the pin; you then run the gate and commit what changed.

§3 · The repository layout

birding/
  kit.json          name · question · content dir · port · engine pin · home · extensions
  Makefile          make check · docs · down · status · site · kit-verify · kit-sync
  kit/              vendored by ckit init, pinned in kit/PIN, never edited in place
    shell/          lib.css · lib.js · search · record viewer · chronicle · annotate · skeletons/
    genres/         GENRES.md (the voice) · genres.json (what is checked)
    craft/          how to build a comparison · diagram · table · timeline · code · figure
    skills/         /present (write a page) · /address (act on annotations)
  content/          notes/ concepts/ entries/ books/ hubs/ projects/ papers/ related/
                    catalog.json · search-index.json · backlinks.json

kit.json is the one file you configure. Beyond name, content, host, port and the ckit pin, two keys are worth setting now: question, one sentence the landing page shows under the name, and home, a page to serve at / instead of the generated landing page (this library's own home is its hub). The keys that extend the kit come last in this book.

Two kinds of file under content/ are never written by hand. The indices (catalog.json, search-index.json, backlinks.json, and a nav.json per book) are generated from the pages. Annotation sidecars, *.annotations.json, are written by the browser or by ckit annotations. Everything else there is a page you author.

Check-yourself: a teammate fixes a typo in the shell's stylesheet directly in kit/shell/lib.css. Why is that a problem?
Their library now renders differently from every other library on the same kit, and nothing but the hash would notice. make kit-verify fails on it. The fix belongs upstream, in content-kit, and arrives in each library through a deliberate re-vendor.

§4 · make check, make docs, make site

The scaffolded Makefile wraps the engine in the targets you will use daily:

TargetRunsFor
make checkkit-verify, then ckit checkthe gate, before every commit
make docsckit upserve the pages in the background on the port in kit.json
make downckit downstop that server
make siteckit export --out dist --base $(BASE)the pages as a static site in dist/
make kit-verifybash kit/verify.shdoes kit/ still match its pin?
make kit-syncbash kit/verify.sh --syncre-vendor kit/ from its pinned sources, on purpose
$ make check
kit ok (content-kit@v0.4.0 )
content lint clean — 0 file(s)
content check ok

$ make docs
serving http://127.0.0.1:5180/  (pid …; `ckit down` to stop)

Open the address it prints. With no pages yet you see the landing page: the library's name, its question, a search link, and one empty group per genre, each saying which ckit new command would fill it. Bottom right is the ✎ Annotate button; it appears only because the engine is serving the page. make docs PORT=8080 overrides the port for one run.

make site writes the same pages as plain files any static host can serve. If the site will live under a path, as a GitHub project site does, say so: make site BASE=/birding/. Pages link the shell and each other with root-absolute URLs (/shell/lib.css, /content/…), and the export prefixes them so they resolve under that path.

Check-yourself: your library will be published at https://example.org/birding/. What do you run, and what would break without the base?
make site BASE=/birding/. Without it, every page would ask for /shell/lib.css at the root of example.org, which is not where the shell was published, and every link between pages would point outside the site.
