Install a library

You leave with the engine installed, a repository set up, every check passing, and its pages in your browser.

§1 · The engine

content-kit comes in two halves. The engine is a command, ckit, that you install once per machine. The kit is a set of rules: the shell (a stylesheet and a script), the genres, the layout guides and three agent skills. The engine copies the kit into each repository you use it in. Start with the engine.

uv tool install git+https://github.com/pierg/content-kit@v0.5.0
$ ckit version
0.5.0

The engine is plain Python, 3.10 or newer, with no dependencies. It needs node for one job: checking a library's books, when it has any. Without uv, clone the repository and run bash install-engine.sh in it. That links the checkout's bin/ckit into ~/.local/bin, and from then on git pull in the checkout upgrades the engine.

Why install the engine, instead of copying it into each repository as the rules are? Because it is code, and code copied ten times has to be fixed ten times. The rules are different. An agent working in a repository must be able to read them there, without looking anywhere else, so they are copied in. The figure shows how the copies stay in step.

Check-yourself: which half lives in the repository, and why?
The kit (the shell, the genres, the layout guides, the skills) is copied into the repository, because an agent working there must read the rules without looking anywhere else. The engine is installed once per machine, because it is code with one place to update.

§2 · ckit init

Point ckit init at a directory, new or existing, and give the library a name:

$ ckit init birding --name "Birding"
vendoring content-kit 0.5.0 -> …/birding/kit
scaffolding
  create  kit.json
  create  Makefile
  create  .gitignore
  set     kit.json name=Birding
  pin     kit.json ckit=0.5.0
pinned  content-kit@v0.5.0
indices generated: content/catalog.json, content/search-index.json, content/backlinks.json, content/threads.json

Read it line by line. It copied the kit into kit/: the shell, the genres, the layout guides, the /present, /address and /curate skills, a hashing tool and verify.sh. It created what the directory lacked: kit.json, a Makefile, a .gitignore, and a folder under content/ for each core genre. It pinned the engine version in kit.json and wrote kit/PIN. It linked each skill from .agents/skills/ to its body in kit/skills/, and pointed .claude/skills at that directory, so an agent opened in the repository finds one copy. It wrote AGENTS.md and the one-line CLAUDE.md that imports it. And it generated the four indices an empty library has.

Running it again is safe. It copies kit/ again, moves the pin, repairs the skill links, and creates only what is missing: your Makefile, your kit.json settings, your AGENTS.md and your pages are kept. It touches only its own files under kit/, so a layer's files there survive.

PIN — definition of record
A library's pin is two records of what it was checked against: the engine version in kit.json (the "ckit" key), which ckit check compares with the engine running it, and a hash of the copied kit/ in kit/PIN, which make kit-verify recomputes. Either mismatch fails, and neither changes except on purpose. 
$ cat kit/PIN
source content-kit https://github.com/pierg/content-kit v0.5.0
hash 667375990f99ed4139e29f659b979c09b3c69d67dd2728c78e5b193a96586593

The source line says where the kit came from, and at which release (or which commit, when the engine runs from a checkout). The pin is why a new engine never changes a library silently: until someone runs ckit init in it again, the gate refuses to run under a different version.

Check-yourself: you upgrade the engine to a new release and run the gate in an old library. What happens, and what is the deliberate fix?
The gate fails with an engine mismatch, because kit.json still names the old version. Run ckit init . with the new engine: it copies the kit again and moves the pin. Then run the gate and commit what changed.

§3 · The repository layout

birding/
  kit.json          name · question · content folder · port · engine version · home · extensions
  Makefile          make check · docs · down · status · site · kit-verify · kit-sync
  kit/              copied by ckit init, pinned in kit/PIN, never edited here
    shell/          lib.css · lib.js · search · review · record viewer · chronicle · annotations · page templates
    genres/         GENRES.md (how each genre reads) · genres.json (what is checked)
    craft/          how to lay out a comparison · diagram · table · timeline · code · figure
    skills/         /present (write a page) · /address (answer annotations) · /curate (organise)
  content/          notes/ concepts/ entries/ books/ hubs/ projects/ papers/ related/
                    catalog.json · search-index.json · backlinks.json · threads.json

kit.json is the one file you configure. Besides name, content, host, port and the ckit version, two keys are worth setting now. question is one sentence the home page shows under the name. home names a page to serve at / in place of the generated home page; this library's home is its hub. The keys that extend the kit come last in this book.

Two kinds of file under content/ are never written by hand. The indices (catalog.json, search-index.json, backlinks.json, threads.json, and a nav.json per book) are generated from the pages. A page's notes, <page>.annotations.json, are written by the browser or by ckit annotations. Everything else there is a page you write.

Check-yourself: a teammate fixes a typo in the shell's stylesheet directly in kit/shell/lib.css. Why is that a problem?
Their library now looks different from every other library on the same kit, and only the hash notices. make kit-verify fails on it. The fix belongs upstream, in content-kit, and reaches each library when it copies the kit again, on purpose.

§4 · make check, make docs, make site

The Makefile that ckit init created wraps the engine in the targets you use every day:

TargetRunsFor
make checkkit-verify, then ckit checkthe gate, before every commit
make docsckit upserve the pages in the background on the port in kit.json
make downckit downstop that server
make siteckit export --out dist --base $(BASE)the pages as a static site in dist/
make kit-verifybash kit/verify.shdoes kit/ still match its pin?
make kit-syncbash kit/verify.sh --synccopy kit/ again from its pinned sources, on purpose
$ make check
kit ok (content-kit@v0.5.0 )
content lint clean — 0 file(s)
content check ok

$ make docs
serving http://127.0.0.1:5180/  (pid …; `ckit down` to stop)

Open the address it prints. With no pages yet, the home page shows the library's name, its question, a search box, and the ckit new command that writes the first page. Open any page and the ✎ Annotate button sits bottom right; it appears only because the engine is serving the page. make docs PORT=8080 uses another port for one run.

make site writes the same pages as plain files that any static host can serve. If the site will live under a path, as a GitHub project site does, say so: make site BASE=/birding/. Pages link the shell and each other with addresses that start at the site root (/shell/lib.css, /content/…), and the export puts the path in front of each.

Check-yourself: your library will be published at https://example.org/birding/. What do you run, and what would break without the base?
make site BASE=/birding/. Without it, every page would ask for /shell/lib.css at the root of example.org, which is not where the shell was published, and every link between pages would point outside the site.
