Extending the kit

You leave able to add a genre, a check, a generated file, a chronicle extractor or a shell page through kit.json; to read how a layer installs itself; to move a 0.3 library across; and to publish a library under a path.

§1 · Ten keys

Everything a library adds to the engine, it declares in kit.json, under one of ten keys. Each key is an extension point: the engine reads it on every run, and the gate checks every declaration before anything uses it.

KeyDeclaresSo that
genresnew genres, or overrides of core onesa new kind of page is scaffolded, checked, catalogued and searchable
checksPython modules exposing CHECKS and REPO_CHECKSa genre can name a check the core lacks
generatorsPython modules exposing generate(repo)a file is generated and drift-checked like the indices
chronicle.extractorsPython modules exposing extract(root, cfg)the chronicle reads a record format the core does not know
shell_pages{"name.html": "path"}a page of your own is served in the shell, at /shell/name.html
links[{"label", "href", "title"}]links appear in the sidebar and on the landing page
refs[{"pattern", "href"}]ids in page text become links
themea stylesheet, or a list of themthe library names the shell's hues in its own vocabulary
classesextra class namesthe lint accepts the classes the theme adds
indicesextra JSON search indices under content/the search page merges them in

Before adding one, ask where it belongs. If every library could use it, it is a mechanism and belongs in the engine; if it only makes sense for your kind of library, it belongs here, in your kit.json, or in a layer. That is the placement rule.

Check-yourself: you misspell a theme's path in kit.json. When do you find out?
At the next ckit check, at stage three: kit.json theme: '…' does not exist. A declaration the engine silently ignored would be worse than none.

§2 · Genres

A genre is an object with the same fields the core genres have. The bird-watching library adds one page per sighting:

"genres": {
  "sighting": { "dir": "sightings", "layout": "flat", "skeleton": "note.html",
                "register": "dated, one bird, one place", "reader": "another watcher checking a record",
                "forbidden": "undated sightings", "after": "hub", "label": "Sightings",
                "checks": { "status": true, "max_words": 300 } },
  "concept":  { "checks": { "max_words": 2000 } }
}

The first entry adds a genre. layout is one of flat (<dir>/<slug>.html), folder (<dir>/<slug>/index.html, with any pages beside it sharing the genre), book-index or book-page. The skeleton is looked for among the shell's skeletons first, then from the repository root. after places its group in the sidebar, the landing page and the search filters (here, right after the hubs) and label names that group. The second entry overrides one check on a core genre, in plain sight, in the one file a reader would look.

genres can also be a list, merged in order, whose items are objects like this one or paths to JSON files holding one. That is how a layer ships its genres in a file of its own while the library keeps its overrides after it:

"genres": ["kit/birdlayer/genres.json", { "concept": { "checks": { "max_words": 2000 } } }]

A genre whose pages must all have the same sections uses the core check require_sections, a list of <h2> ids that must appear in that order. Extra sections are allowed; a missing or misplaced one is reported by its id.

Check-yourself: after declaring the sighting genre, what does ckit new sighting 2026-05-03-swifts create?
content/sightings/2026-05-03-swifts.html, copied from the note skeleton, with the sighting's voice card printed beside it. After ckit lint, a Sightings group follows the hubs in the sidebar.

§3 · Checks

A check the core does not have lives in a Python module you register under checks. The module exposes one or both of two tables:

# ext/checks_birding.py
import re

PLACE = re.compile(r'<meta name="place" content="[^"]+"')

def require_place(ctx):
    """Page check: a sighting names where it happened."""
    return [] if PLACE.search(ctx.served) else [f"{ctx.rel}: a sighting needs <meta name=\"place\" content=\"…\">"]

def no_empty_sightings(repo):
    """Repository check: run once per lint."""
    d = repo.content / "sightings"
    return [] if not d.is_dir() or any(d.glob("*.html")) else ["content/sightings/: declared but empty"]

CHECKS = {"require_place": require_place}
REPO_CHECKS = {"no_empty_sightings": no_empty_sightings}
"checks": ["ext/checks_birding.py"],
"genres": { "sighting": { "checks": { "require_place": true } } }

A page check runs wherever a genre names it, exactly like a core check, and receives a context: ctx.page (the file), ctx.rel (its path, for messages), ctx.text (the raw source), ctx.served (what a reader is served: comments, scripts and styles removed), ctx.genre, ctx.arg (the value the genre gave the check) and ctx.repo and ctx.cfg. A repository check gets the repository and runs once per lint. Both return a list of problems, each a string beginning with the path it is about; an empty list means clean.

If a genre names a check that neither the core nor any registered module provides, the lint refuses to run:

genre 'sighting' names check 'require_place', which is not a core check and no module in kit.json `checks` provides — register the module that implements it, or drop the check from the genre

And hold the check to the fixture rule from the gate chapter: before you trust it, plant a page that breaks it and watch it fail by name.

Check-yourself: why does require_place search ctx.served rather than ctx.text?
So a place written only inside an HTML comment does not count. A check should pass on what the reader actually gets, not on markup that never renders.

§4 · Generators

A generator writes a file the library commits and the gate keeps current. It is a module with one function, registered under generators:

# ext/gen_count.py
def generate(repo):
    pages = sorted((repo.content / "sightings").glob("*.html"))
    return {"content/sightings.json": {"count": len(pages), "pages": [p.stem for p in pages]}}

It returns a map from repository-relative path to data: a string is written as it is, anything else as indented JSON. ckit lint writes the files alongside the core indices, and ckit check fails when one is stale, exactly as for the catalog. A generator may not write outside the repository, may not claim a file the engine generates itself, and may not claim a file another generator already writes.

Check-yourself: you add a sighting page but forget to run ckit lint. What does the gate say about content/sightings.json?
That it is out of date, in the same list as the catalog and the search index. Run ckit lint and commit it with the page.

§5 · Chronicle extractors

The chronicle reads dated headings from the record on its own. When a library keeps history in a shape the core does not know, an extractor turns it into events:

# ext/sightings_x.py
KINDS = [{"name": "sighting", "hue": "teal", "story": False}]
CARDS = {"view": "species", "label": "Species", "kind": "sighting", "empty": "No sightings yet."}

def extract(root, cfg):
    events, cards = [], []
    for p in sorted((root / "content" / "sightings").glob("*.html")):
        date, title = p.stem[:10], p.stem[11:].replace("-", " ")
        href = f"/content/sightings/{p.name}"
        events.append({"date": date, "kind": "sighting", "title": title, "href": href})
        cards.append({"title": title, "href": href, "date": date,
                      "fields": [{"label": "First seen", "text": date}]})
    return {"events": events, "cards": cards}
"record": ["log/2026.md"],
"chronicle": { "sources": ["log/"], "extractors": ["ext/sightings_x.py"] }

extract returns events and, optionally, cards. Every event needs a date, a kind, a title and an href, and its kind must be declared, either as a core tag or in some extractor's KINDS; each kind names a shell hue and whether the Story view shows it. CARDS names a third view of the chronicle page, one card per long-lived thing the history tracks (here, one per species first seen); only one extractor may supply cards. An event of an undeclared kind fails the lint by name.

Check-yourself: with "story": False, where does a sighting appear on the chronicle page?
In the Timeline view, which shows every event, and as a card in the Species view. Not in Story, which shows only the kinds marked for it.

§6 · Shell pages, links, refs, theme, classes, indices

The remaining six keys change what the reader sees.

"shell_pages": { "board.html": "ext/board.html" },
"links":       [ { "label": "Board", "href": "/shell/board.html", "title": "This season at a glance" } ],
"refs":        [ { "pattern": "S-\\d+", "href": "/shell/record.html?p=log/2026.md#{id}" } ],
"theme":       "assets/theme.css",
"classes":     ["sw-marsh", "sw-moor"],
"indices":     ["content/club-index.json"]
  • shell_pages serve a file of your own at /shell/<name>, beside the search page and the chronicle, and export it with the site. A name may not shadow one of the shell's own files. home may name a shell page, which then becomes the library's front door.
  • links sit at the top of the sidebar and on the landing page.
  • refs turn ids that match a pattern into links wherever they appear in a page's text, inline code included; text inside <pre>, links and headings is left alone. The pattern may use only non-capturing groups, because the whole match is the id, and the href must contain {id}.
  • theme is served as /shell/theme.css, which the shell's stylesheet imports first. It maps your own names onto the shell's hues, and may style widgets only your pages use:
/* assets/theme.css */
.hb { --marsh: var(--teal); --moor: var(--amber); }
.hb .sw-marsh { color: var(--marsh); font-weight: 700; }
.hb .sw-moor  { color: var(--moor);  font-weight: 700; }
  • classes registers the class names the theme adds under a shell prefix (sw-, lane-, v-, ev-, st-, hb-), so the lint accepts them on your pages.
  • indices are extra search indices, JSON files under content/, that the search page fetches and merges with the library's own.
Check-yourself: your theme defines --marsh and a class sw-marsh, but you forget the classes key. What fails, and what does not?
Every page using class="sw-marsh" fails the lint as an unknown shell class. A page using var(--marsh) passes, because the theme declares the token.

§7 · How a layer installs itself

A layer is a repository of conventions for one kind of library, installed on top of the kit through the same ten keys. One exists: lab-kit, the record discipline for research run by agents. A library whose rules no other library shares keeps them in its own repository instead, registered through the same keys. The engine knows neither.

An installer is given only ckit, and does four things:

  1. Runs ckit init on the repository, so the kit is vendored and the engine pinned before anything else.
  2. Copies its own rules beside the kit, under its own directory in kit/: its genre file, skeletons, check modules, shell pages. When it needs one of the kit's own files (a template, the migration theme), it asks ckit where, which prints the directory the engine vendors from, wherever the engine was installed.
  3. Registers them in kit.json: its genre file first in the genres list, its modules under checks, generators or chronicle.extractors, its pages under shell_pages.
  4. Adds its line to kit/PIN, source <name> <url> <ref>, and recomputes the hash with bash kit/verify.sh --repin, so the layer's files are covered by make kit-verify too.

The pieces are built to allow this. ckit init touches only its own paths under kit/ and keeps every other kit's source line when it re-pins, so re-running it never erases a layer. make kit-sync re-vendors every kit in kit/PIN, in order: content-kit through ckit init, every other kit by running the install.sh at the root of its checkout with the repository as argument. It finds each checkout through an environment variable named after the kit ($CONTENT_KIT for this one), the path recorded in the pin if it exists, ckit where for content-kit, or a sibling directory of the same name.

Check-yourself: after a layer is installed, you re-run ckit init . to take a new engine. What happens to the layer's files and its pin line?
Both survive. ckit init re-vendors only its own directories, keeps the layer's source line, and re-hashes the whole of kit/, the layer's files included.

§8 · Moving a 0.3 library across

Version 0.4 renamed the config file, named the shell's colour tokens for their hues, and moved domain-specific widgets out of the shell. A library written against 0.3 moves across in a few steps:

uv tool install git+https://github.com/pierg/content-kit@v0.4.0
git mv lab.json kit.json
ckit init .

lab.json is still read until 0.5, with one deprecation line per run, but ckit init is what re-vendors the kit and moves the pin to 0.4.0. If the pages use the old colour names (the set register --reach --cert --target --slack --leak, now --teal --indigo --blue --amber --red; the role register --gen --judge --world, now --azure --violet --orange) or the widgets that left the shell, a migration theme keeps them rendering exactly as before:

mkdir -p assets && cp "$(ckit where)/templates/theme-fv.css" assets/theme.css
"theme": "assets/theme.css",
"classes": ["sw-reach", "sw-cert", "sw-target", "sw-slack", "sw-leak", "sw-gen", "sw-judge", "sw-world",
            "lane-reach", "lane-cert", "lane-target", "lane-slack", "lane-leak", "lane-gen", "lane-judge", "lane-world"]

theme-fv.css maps each old name onto its hue and carries the removed widgets verbatim. The engine's selftest serves it to a page written in the old vocabulary and proves that page lints clean, so the path is tested, not just described. Then regenerate the indices (their shape changed in 0.4), run the gate, and commit:

ckit lint && make check
Check-yourself: after the move, a page still uses the old role token for the actor that decides. Without the migration theme, what does the lint say, and what is the lasting fix?
That the token is unknown: nothing declares it any more. The migration theme declares it again; the lasting fix is to rewrite the page with the hue it now maps to, --violet, and drop the old name.

§9 · Publishing under a path

ckit export writes the library as static files any host can serve:

ckit export --out dist --base /birding/

Into dist/ go: an index.html (the landing page; or a redirect to the home page, when home names one; or the shell page home names), the shell without its skeletons, theme.css and every declared shell page, the content tree with its generated indices, the record files, and a .nojekyll so GitHub Pages serves every path as it is. Annotation sidecars stay home: review happens against the served repository, not the published copy.

--base is for a site served under a path, such as a GitHub project site. The export prefixes every root-absolute href, src, action and poster attribute, and every root-absolute CSS url(), in the exported HTML and CSS, so /shell/lib.css becomes /birding/shell/lib.css. JSON indices and scripts are left alone: the shell works out its base from the address of its own script, so nothing else needs configuring. The source tree is never touched.

Two refusals protect you. The export will not write inside the content, the shell or kit/, and it will not replace a non-empty directory it did not write itself. make site BASE=/birding/ runs the same export into dist/. To preview a site built for a path, export it into a directory of that name and serve its parent with any static server:

ckit export --out preview/birding --base /birding/
python3 -m http.server -d preview       # then open http://localhost:8000/birding/

This library is published the same way: its CI gates the pages with ckit check, exports them with --base set to the repository's name, and deploys the result to GitHub Pages.

Check-yourself: after exporting with --base /birding/, why do the links inside content/catalog.json still start with /content/, and why does the sidebar still work?
JSON is not rewritten. The shell reads its base from the address it loaded lib.js from (/birding/shell/lib.js) and prefixes every URL it builds from the catalog with it.
