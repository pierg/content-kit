Prior art

What others have built or proposed for agent-maintained knowledge, documentation structure, prose checking, publishing notes, and annotating the web, each on its own terms, with our reading kept separate.

The works

One row per work. Both columns are theirs, summarised neutrally from the linked source. Every link below was opened on 2026-09-22 and checked to be the work described; where a detail could not be confirmed from the source, the row leaves it out rather than guessing.

WorkWhat they didWhat they claim
Andrej Karpathy — "LLM Wiki"
idea file, GitHub gist, April 2026
gist.github.com/karpathy/442a6bf5…		 Describes a pattern for a personal knowledge base that an LLM agent builds and maintains: immutable raw sources, a wiki of interlinked markdown pages the agent writes, and a schema file of conventions (such as a CLAUDE.md). Three operations: ingest a source into the wiki, query the wiki, and lint it for contradictions, stale claims, orphan pages and missing cross-references. An index file and a log file help the agent navigate; Obsidian is suggested for browsing. The wiki is a persistent, compounding artifact, so knowledge is compiled once rather than re-derived from raw sources on every question. The human curates sources and asks questions; the LLM does the summarising, cross-referencing and bookkeeping. Shared as an idea for each reader's agent to build, not as code.
Daniele Procida — Diátaxis
diataxis.fr		 A framework that sorts technical documentation into four kinds by the reader's need: tutorials (learning), how-to guides (a task), reference (information) and explanation (understanding), with a distinct approach to content and form for each. Organising documentation around those four needs improves it for readers and authors alike; the framework is light-weight and easy to apply, and has been adopted across hundreds of documentation projects.
Write the Docs — "Docs as Code"
writethedocs.org/guide/docs-as-code		 A community guide to writing documentation with the same tools as code: issue trackers, version control, plain-text markup, code review and automated tests. Writing docs this way brings writers into development teams and makes documentation a shared responsibility of writers and developers.
Vale
vale.sh · github.com/vale-cli/vale
MIT licence		 A command-line prose linter. A style is a folder of YAML rules (substitutions, terms, patterns); Vale parses the markup (Markdown, AsciiDoc, reStructuredText, HTML and others) and applies the rules to the prose, in editors and in CI. It brings code-like linting to prose, letting teams turn their style guide into automated checks. Because it parses markup instead of guessing at it, rules can target headings, lists or table cells and skip code and URLs.
Quartz (jackyzha0)
quartz.jzhao.xyz · github.com/jackyzha0/quartz
MIT licence		 A static site generator that turns a folder of Markdown notes, Obsidian-compatible, into a website with wikilinks, backlinks, a graph view, full-text search, popover previews and transclusion. A fast, batteries-included way to publish a digital garden: interlinked notes online with little configuration.
Hypothesis
web.hypothes.is · github.com/hypothesis/client
client: BSD 2-clause licence		 An annotation service with an open-source client: readers highlight and comment on web pages and PDFs through a browser client. Its 2013 post "Fuzzy Anchoring" describes storing each annotation's target three ways (a range in the markup, character offsets, and the quoted text with its context) and re-attaching it by trying each in turn, ending in fuzzy text matching. Combining selectors with fuzzy matching lets annotations survive changes to a document's structure and content. The service presents itself today as a social annotation platform for teaching and teams.
W3C — Web Annotation Data Model
W3C Recommendation, 23 February 2017
w3.org/TR/annotation-model		 A standard model for annotations: a body, a target, and selectors that say which part of the target is meant, among them the TextQuoteSelector, an exact quote with an optional prefix and suffix to tell repeated passages apart. A common model lets annotations be shared and reused across platforms rather than locked to one tool.
Jeremy Howard — llms.txt
proposal, first published 3 September 2024
llmstxt.org		 Proposes a markdown file at a site's /llms.txt with curated guidance and links for language models, and markdown versions of pages beside the HTML ones. Web pages are built for people, and their navigation and layout waste a model's context; a concise, curated text serves agents better at the moment they use a site.
AGENTS.md
agents.md		 An open format: a markdown file at a repository's root (and, in a monorepo, in subprojects, the closest one winning) holding the instructions a coding agent needs: build steps, tests, conventions. A "README for agents": one predictable place for agent context that keeps the human README uncluttered, supported by a growing set of coding-agent tools.

Our reading

This section is ours, not theirs: what each work settles or leaves open for the question of how agents write pages that keep belonging.

The LLM wiki is the closest in intent. Both have an agent writing an interlinked body of pages for a human, with a lint pass over it. The differences are in what is made mechanical. There the page conventions live in a schema file the agent reads, and the lint is a health check the agent performs with judgment, catching contradictions and stale claims. Here the conventions are genres with a written voice, and the lint is a gate that fails a commit, but checks only structural proxies: it cannot see a contradiction. The wiki also treats ingesting raw sources as a first-class operation, which content-kit does not; content-kit adds a channel the wiki lacks, from the reading human back to a later agent, through annotations.

Diátaxis and the genres answer different questions. Diátaxis sorts by what the reader needs to do; content-kit's genres sort by the role a page plays in a library (a claim, a definition, a map, a step in a sequence), and attach checks to each. They overlap (a chapter behaves like a tutorial, a concept like reference), and the core has no how-to genre; a library that wants one can declare it with a fixed section order through an extension point. Diátaxis is guidance for writers; the genres try to make the checkable part of such guidance a gate.

Docs as code is the ground content-kit stands on, with two changes: the main author is an agent rather than an engineer, and review happens on the rendered page rather than in a diff.

Vale checks what the gate leaves to reviewers. The gate checks form and genre proxies, never wording; Vale checks wording against a style and parses HTML. They look complementary, since a Vale style could carry the part of a genre's voice that is checkable as vocabulary. Nobody here has tried running Vale over a content-kit library, so that is a possibility, not a result.

Quartz shares the reader's affordances and not the pipeline. Backlinks, search and hover previews are in both; wikilinks, transclusion and the graph view are Quartz's alone. Quartz builds a site from markdown; content-kit serves hand-written HTML with no build. Why is argued in Why hand-authored HTML.

From Hypothesis and the W3C model, content-kit borrows the anchor and refuses the fuzziness. Its sidecars use the TextQuoteSelector shape as specified. It does not re-attach a quote that has changed: an exact match (with prefix and suffix to choose among repeats, and a whitespace-insensitive fallback) either finds the passage or the gate fails. Hypothesis has to survive pages it does not control; a library controls its pages, so it can require that an open note be answered before its passage is rewritten. Storage differs for the same reason: a committed file beside the page rather than a hosted service.

llms.txt and AGENTS.md treat agents as readers of documentation; content-kit treats them as its writers. They meet at the authoring rules: a repository's AGENTS.md is a natural place to tell its agent to use the /present skill.

What nobody has measured, as far as this page's sources show: whether mechanical genre checks make agent-written pages better than written guidance alone does. The design law predicts they do; that prediction has not been tested against a control.
