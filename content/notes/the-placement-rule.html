The placement rule

Status: LIVE — mechanisms below, conventions above: if it makes sense in a code repository's docs, it belongs in content-kit; if it only makes sense in a lab or a personal library, it belongs in a layer.

Mechanisms below, conventions above.

content-kit is mechanism: a genre table, a gate, a shell, generated indices, the annotation loop, ten extension points. A layer is convention: what a research lab's record must contain, what a personal library's topics are. The test for which side a feature falls on is concrete. Would it make sense in the docs folder of an ordinary code repository? A status line on every page, a definition of record, indices that must be current, a reader's note on a rendered page: yes, so they are in the engine. A rule that every number cite a row of a lab's record, flashcard revision over a personal library: no, so they live in a layer and reach the engine through kit.json.

The rule protects every library from every other. An engine that learns one layer's vocabulary imposes it on all the rest, as defaults nobody asked for and checks that fire on pages they were never meant for. Version 0.4 applied the rule to the engine itself: a genre, record checks, and domain colour names and widgets that only one kind of library used left the engine for the layers and a theme, and came back through the extension points. The engine now knows neither of the two layers that exist, lab-kit and folio.

It also says where a new idea goes. A mechanism every library could use goes upstream, into content-kit, with a fixture that breaks it (the design law). A rule only your library needs goes in your kit.json. A convention several libraries of one kind share is a layer.
